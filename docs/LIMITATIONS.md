# Limitations

A standalone, honest accounting of what this build does not know, does not
prove, and has not measured — independent of the future `/demo` sales
page (Spec section 10; M3), which will generate its own on-page `/limits`
panel from the same `stubbed[]`/`simulated[]` arrays this file references
by hand. Read together with `docs/DEVIATIONS.md` (why the repo diverges
from the spec) and `docs/M0-REPORT.md`/`docs/M1-REPORT.md` (what was
actually run and measured each milestone).

## Nothing was ever sent, anywhere, by any run committed so far — including the real recordings

Every run in `content/runs/` — `mode: "simulator"` or `mode: "recording"`
alike — lists `gohighlevel`, `slack`, `google-sheets` and `voice-ai` as
`stubbed`. For the two recordings, n8n itself genuinely executed
(`real: ["n8n", "webhook", "normalize", "wait", "branch"]`), but every call
those nodes made went to `capture/stubhouse` on `127.0.0.1`, not a live
vendor — see `capture/README.md` for exactly how. No SMS, no email, no
Slack message, no spreadsheet row, and no phone call exist outside this
repo's committed JSON, in any run, ever. The composed SMS/email/Slack text
you'll see on `/demo` was either generated by `packages/engine` (Simulator
tab) or genuinely composed by n8n's own nodes and handed to stubhouse
(Recording tab) — and went nowhere either way.

## The stub response shapes are modeled, not verified against a live API — true for the recordings too

`packages/engine/src/stubs.ts`'s own header: "Every shape here is MODELED
from the public API documentation. None has been verified against a live
LeadConnector, Slack or Sheets endpoint." `capture/stubhouse` reuses this
exact module as its response generator (`capture/README.md`), so this
caveat is not just a simulator-era limitation the recordings outgrew — a
real n8n Slack/Sheets/GHL node call answered by a shape that has drifted
from the live API would not be caught by anything in this repo, recording
included. If GoHighLevel's real `contacts/upsert` response shape has
drifted from its public docs, nothing here would currently catch that —
there is no live API in the loop to disagree with, in either mode.

## The simulator's per-node timings are still a stated assumption — the recordings are not

`packages/engine/src/timing/modeled-v1.json` remains exactly what its own
note says: "every value here is a stated assumption, not a measurement,"
each with its own `basis` string rather than a citation. Its own comment
anticipated this table being *replaced* at M1 with one derived from a real
capture's timings — this session's build brief scoped M1 to the capture
rig, the two recordings, and the Recording tab, and explicitly deferred
that swap (see `docs/DEVIATIONS.md`). So: the two real recordings' node
timings (`content/runs/rec-medspa-*/run.json`) are genuine measurements
from one real n8n execution each — not projected across a distribution,
not reused as the simulator's new assumption set. The five simulator runs'
timings remain the pre-M1 modeled numbers, now sitting *next to* real
measurements on the same `/demo` page rather than reconciled against them.
`/`'s hero number switched to the recording's measured figure specifically
so the strongest available claim is the one on screen — see
`docs/DEVIATIONS.md`.

## The 42-hour claim is a 2011 study

`Oldroyd, McElheran & Elkington, "The Short Life of Online Sales Leads,"
HBR, March 2011` — audited 2,241 companies. It remains the most-cited
figure in this space because vendor audits keep replicating the pattern
(see `service-samples/automations/speed-to-lead/README.md`'s own honest
caveat, which this demo's hero copy echoes), but it is fifteen years old at
the time of this build and the exact multiplier should be treated as
directional. This demo does not claim its own before/after conversion
lift anywhere — no client, real or fictional, has a measured before/after
number to report.

## Two of seven committed runs render on the site as a full ledger page

`/demo` shows `rec-medspa-happy` (Recording tab, default) and
`sim-medspa-happy` (Simulator tab). `rec-medspa-slack-401` is linked (its
`run.json` and `execution.json` both download from `/demo`) but has no
ledger page of its own. The other four committed, golden-tested simulator
runs (a revoked Slack token, a GoHighLevel 429, a duplicate webhook
delivery, a reply-check timeout) exist as data and as engine test coverage
but are not yet reachable from any page — see `docs/DEVIATIONS.md`.

## No accessibility audit has been run

Semantic HTML was used throughout (`<table>` with `<caption>`/`scope`
headers for the ledger, a labeled `<nav>`, visible `:focus-visible`
outlines, no color-only status — every status also carries plain text),
and `/demo`'s M1 tab switcher is real, keyboard-reachable radio/label
markup (not `display:none` divs toggled by inaccessible JS), but none of
that is a WCAG 2.2 AA conformance claim — it's still a good-faith
baseline. The tab switcher is specifically *not* ARIA `tablist`/`tab`/
`tabpanel` (no roving tabindex, no arrow-key-only navigation model — see
`docs/DEVIATIONS.md`). The animated, keyboard-complete player, `aria-live`
milestone announcements, reduced-motion handling, and measured contrast
numbers Spec section 13 requires are explicitly M2/M3 scope (the
`a11y-audit` skill / the accessibility-engineer agent, run against a
*live* deployed interface — this repo has not been deployed).

## No performance audit has been run

The built site is small by construction (53 KB total, zero JS, one 5.9 KB
CSS file — see `docs/M0-REPORT.md` for the exact numbers from this
milestone's build), but no Lighthouse run, real-device test, or Core Web
Vitals measurement has happened. Spec section 13's ≥95-in-all-four-
categories gate is explicitly bound to the *deployed* URL in CI (M3); there
is no deployed URL yet.

## No abuse-case or load test has been run

Spec section 7's two abuse cases (single-IP burst, distributed low-and-
slow) require the Worker's quota logic and D1 counters, neither of which
exists yet (M2). Nothing about cost safety has been load-tested; it has
only been reasoned about (`scripts/check-bindings.mjs` enforces the
binding allow-list that makes those abuse cases bounded *once M2 exists*).

## Everything about "Radiant Aesthetics" is fictional

The business, its Slack workspace, its Google Sheet, its GoHighLevel
sub-account, and the lead "Alex Rivera" (`content/placeholders.json`,
`scripts/generate-runs.ts`) are invented for this demo. No client, past or
present, is named or implied anywhere in this repo.
